# 怎么写

## 先定义，再展开

一篇文档的前三句要回答：它是什么、谁在用它、它做什么。定义要精确到读者能拿它判断一个新例子算不算。

反例（真实，`docs/sins/regions/丘脑.md` 改前）：

> 丘脑治理**当前一次 Main 请求**：组织 owner-backed facts、稳定认知提示与模型可见 capability surface。它不拥有 durable truth，不替 Main 做意图推断、价值判断、优先级、方案选择或完成决策。

半句定义加五个"不"。读者读完知道它不做什么，仍然不知道该拿它做什么。

改后：

> 丘脑决定 Main 这一次请求看到什么：owner-backed facts、稳定认知提示、模型可见的 capability surface。意图、价值、优先级、方案和完成由 Main 判断。

同一件事，换成正面陈述：谁的职责一句话说完，另一个 owner 顺带点名，不需要五连否定。

否定只在一种情况下保留：读者很可能以为它做了这件事，而事实相反，且误会会造成实际损失。

## 读者是扫着看的

他不从头读到尾。他搜到一个词，落到某一页，扫前两段，决定要不要往下看。

所以：

- 第一段就说清这文件讲什么、什么情况下要读它。
- 小节标题写成会被搜到的词。「网络连不上怎么办」，不是「故障处理」「常见问题」「其他」。
- 一段一个意思。超过五行就拆；拆不动说明两个意思缠在一起了。

## 示例要能直接改

泛化的示例不算示例。76 人的对照实验里，与真实任务程序结构高度相似的示例在有效性、效率和满意度上全面占优，还少出安全漏洞；抽象通用的示例没有正面效果（[arXiv 2004.03973](https://ar5iv.labs.arxiv.org/html/2004.03973)）。所以示例用真路径、真参数、真命令，从要解决的那个任务抄一遍下来，不从 `foo`、`bar` 起手。

一个主题留两扇门：一扇进概念，一扇进代码。读者要么先要全局再动手，要么直接抄示例、跑不通才回头读解释——访谈里两派人数相当，眼动观察的 11 人里 6 人先看概念、5 人直奔示例。所以同一页里既要说清「这是什么、为什么这样」，也要有一段能复制的示例。

## 写给 agent 看的页

agent 只读它抓到的那一段，读不到你没写的那句。所以每段要能单独读懂：主语是谁、在什么范围成立、出错时什么表现。别指望它顺读全文再拼回来。

能指的一律指。字面量按 [`README.md`](../README.md) 判据 1 换成指向真源的一跳：写「见 `src/x.ts` 的 `foo()`」，不把参数默认值抄一遍。抄一遍就等于给 agent 备了一份会过期的答案，而它不会去核。

## 陈述句，不写祈使句

写「key 不存在时返回 null」，不写「你必须确保 key 存在」。

祈使句在陈述要求，陈述句在陈述事实。事实能被验证，要求只能被违反。

同理，写「这段代码在 Windows 上会死锁，因为 X」，不写「注意不要在这里写死锁代码」。

## 路径要能点开

GitHub 上只有 markdown 链接能点。裸反引号里的路径是给眼睛看的，不是给鼠标用的。

写成链接，读者能直接点：

```markdown
- [docs/README.md](docs/README.md) — 文档入口
```

写成裸反引号，页面上就是一串灰字，读者得自己复制路径再拼一遍 URL：

```markdown
- `docs/README.md` — 文档入口
```

相对路径按文件自己的位置算：

| 在哪个文件里写 | 指向 `docs/README.md` 的写法 |
|---|---|
| 根 `README.md` | `docs/README.md` |
| `docs/` 里的文件 | `README.md` |
| `docs/hardware/` 里的文件 | `../README.md` |

别的仓库的东西写成反引号，前面带上仓库名：`SiNS:docs/sins/regions/丘脑.md`。跨仓库的相对链接在 GitHub 上打不开，两个仓库不在同一个站点里；要能点就贴完整 URL，并接受它会跟着对方分支变化。

## 不要靠加粗制造重点

加粗、全大写、「注意」「重要」「必须」「绝对」——每个都用过一遍之后，就没有东西是重要的了。

一段里值得加粗的通常不超过一处。整段都加粗等于没加粗。

## 不解释自己

「本文档介绍」「如上所述」「综上所述」「下面将说明」。这些是文档在说自己，不是在说事情。

删掉之后通常什么都不缺。

## 一个仓库一种语言

同一份文档里混中英文，两种语言都读不顺。上游项目自带的多语言版本是例外，那种情况按上游的机制走。

不要把同一篇文档翻译成两份平行维护。两份迟早不一致，而且没人知道该改哪份。

## 表格不超过四列

超过四列，读者要在横向滚动里丢行。拆成两张表，或者改成小标题加分点。

## 长度由读者需要多少决定

短不一定是好文档，长也不一定是坏文档。一份完整的部署说明写三千字是正常的。

判断标准在 [`what-good-means.md`](what-good-means.md)：删掉这句，读者会失去什么。
