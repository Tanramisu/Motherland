# 蓝图

蓝图说的是**这东西最终要长成什么样**。它是开发依据：读完应当知道下一步该写哪块代码、验收标准是什么。

蓝图不是愿望清单。"应该更智能""需要更完善"这种句子放进来，蓝图就失去了用途——没人能据此判断做完了没有。

## 四段

### 一、目标形态

最终系统由哪几块组成、每块负责什么、用户看到的行为是什么。用「它就是……」「它由……组成」这类现在时表述，不写「希望能够」。

一段话加一张结构图（文字列表也行）。读者要能凭这段判断：某个功能属于哪一块，不属于哪一块。

### 二、为什么是这个形态

和备选形态比，这个形状解决了什么、放弃了什么、放弃了为什么可接受。

这一段的价值在于：半年后有人想改结构，他得先知道你当时为什么没选另一条路。没有这一段，每个后来的人都会重推一遍。

### 三、验收判据

每一条都要能被观察或执行：命令、输出、数值、界面行为。

- 能写：「`gen-cordis-catalog` 在新增一个 service 后必须先报缺失映射，补齐后生成一整块 region。」
- 不能写：「目录生成要健壮、可维护。」

判据条数控制在十到二十条。超过二十条说明目标形态还没收敛。

### 四、差距表

| 蓝图条目 | 当前状态 | 缺什么 | 下一步动作 |
|---|---|---|---|

这张表是蓝图的实用性所在：它是「我现在该开发什么」的答案。每行都要有下一步动作，写不出动作的行说明要么已完成（移出去），要么目标还没想清楚（回去改第一段）。

## 与当前实现的分工

| | 蓝图 | 当前实现 |
|---|---|---|
| 时态 | 它将是 / 它要成为 | 它是 |
| 读者 | 决定下一步做什么的人 | 想知道现在怎么运转的人 |
| 内容 | 组成、理由、判据、差距 | 模块、数据流、真实数值、已知缺口 |

两张页面的连接只有一个方向：当前实现的一句话把读者送到蓝图，蓝图用差距表把读者送回当前实现的具体条目。两边不复制同一段文字。

## 真实样例的骨架

SiNS 的丘脑（Thalamus）可以这样写：

**目标形态**：丘脑在最终组卷位置工作，决定一次 Main 请求带上哪些 capabilities、Skill 正文和长期证据；它读的是最终接纳后的 message batch，不是早期的 assembly 输入。

**为什么**：现在的接缝是 `system-prompt/assemble`，它早于 `agent/pre-step` 的最终接纳，也拿不到最终 batch。改到组卷位置会牵动 agent-loop 的调用顺序，代价是一次跨包改动；收益是选择结果与真正发出的请求一致。

**验收判据**：本轮输入触发一次 composition decision；request 里的 tool schemas 与 Skill 正文符合该决策；下一轮或 resume 不出现过期能力；关掉插件后 assembly 回到原始结果。

**差距表**：`system-prompt/assemble` 早于最终接纳 → 只能做早期 tool gating → 需要在 `agent/pre-step` 之后新增一个组卷接缝 → 改 `agent-loop` 的调用顺序并补一个 session 事件。

## 不许出现的写法

- 「期望形态」「理想架构」「部分 carrier」「还不是 final owner」——相对句让读者自己去比，等于没写。
- 「后续需要考虑……」「有待完善」——没有动作的空格。
- 把现状塞进蓝图：蓝图里出现"目前""暂时""已经支持"，说明两页混了。
- 蓝图里写实现细节：函数名、字段名、事件名属于当前实现与参考。蓝图写组成和判据。

## 谁来写

蓝图由知道目标的人写，不由读代码的人推。读代码只能推出"现在是什么"，推不出"要什么"。目标材料不足时，写成「待定 + 候选方案 + 需要谁决定」，不要编一个看起来完整的目标。
