# 改与删

## 三条规则

**过时即改。** 同一个文件里的旧说法直接替换成新的。不写「已废弃」「以前是 X，现在是 Y」。

**完成即删。** 计划、路线图、进度记录、验收清单、审计报告，任务结束就没有读者了。归宿是 PR 描述和 commit message。复盘不在这一列：它记的是过程，按记录类保留，见下面「什么时候可以留下历史」。

**被取代即删。** 新文档覆盖了旧文档的职责，旧文档删掉。不保留是为了「万一有人还在引用」——真有人引用，改那条引用。

## 归档不是收拾

把文件移进 `archived/`，只是让它换个位置继续占地方，而且从此不会有人再打开它。

看起来处理过了，实际是把清理推迟到了永远不会到来的那一天。SiNS 的 `.agents/notes/archived/` 里有 637 篇这种状态的笔记。

真正只有两个结果：**修好，或者删掉。**

犹豫的时候，通常不是不知道该不该删，而是还没决定这份文档当前是真是假。判断一遍，然后动手。

## 什么时候可以留下历史

只有一种情况：**变化过程本身就是知识。**

测试方法：删掉它，未来会不会有新人重新踩同一个坑？会，那它值得留。但要改写一遍——写的是「这个坑是什么」，不是「我们当时怎么处理的」。前者对新人有用得多。

## 改代码的那一次顺便改文档

过期的修法只有一种是被数据证实有效的：让文档改动和代码改动落在同一批改动里。AI 提交的 PR 里 63.2% 改代码不带文档；某个文件这次漏了文档，90 天内被补回的比例只有 24%，而本来就带文档的是 48%（[arXiv 2610.27381](https://arxiv.org/html/2610.27381)，29,669 个 PR）。漏掉的那次大概率不会有第二次机会——不是绝对，是同一个文件被回头补上的概率减半。

顺手的判据：这次改动让某份文档变假，改它的成本算不算「顺手」。不算，就说明这份文档不该存在（删），或者它描述的东西不归它管（搬）。别指望季度审计——内容审计的实测成本约 90 分钟一页。

## 合并与拆分

两个文件讲同一件事，合并成一个，删掉另一个。不留重定向文件、不留「已合并至」提示。

一个文件讲两件事，按类型拆开：蓝图归蓝图，现状归现状，决策归决策。按章节拆是错的——拆完还是同一页的两个主题。

## 删之前检查两件事

1. **有没有只此一份的事实。** 那些信息换个地方还有吗？
2. **有没有链接指过来。** 删掉之后哪些文档会出现断链。

就这两件。不需要额外备份（git 历史就是备份），不需要墓碑文件，不需要在 changelog 里记一笔。

## 删除的边界

只管自己这个仓库的文档。

别的仓库的文档归它的 owner。已经归档的仓库不动。

有一条例外：**有对外 URL 的文档删之前留一跳。** 私有仓删了只是自己少一页；公开页删了，别人的书签和搜索结果变成死链，读到的信号是「这个项目死了」。做法是在同类页面里写一句「原来讲 X 的那页并进了这里」，或者加一次跳转。全网数据里 2013 年存在的网页到 2023 年有 38% 已经打不开（[Pew 2024](https://www.pewresearch.org/wp-content/uploads/sites/20/2024/05/pl_2024.05.17_link-rot_report.pdf)），自有文档没必要加入这个统计。
