# 十种文档

每种文档回答一个问题，放一个地方，有一个长度。混在一起，读者就得自己判断哪句是目标、哪句是现状、哪句是理由——这正是坏文档的主要来源。

类型是命名约定，不是必须填满的格子。没有对照实验证明按类型分目录能提高任务成功率：架构文档写成叙述体还是套结构化模板，65 人的理解任务成绩没有显著差异，主导因素是「之前碰过这份代码」（[ESE 2023](https://www.cs.mcgill.ca/~martin/papers/2023-ese.pdf)）；Diátaxis 自己的文档也说它没有理论证明（[foundations](https://diataxis.fr/foundations/)）。有证据的只有两条：模板的空位要少，不要做强制表单。

| # | 类型 | 回答 | 目录 |
|---|---|---|---|
| 1 | README | 这是什么、怎么跑 | 仓库根 |
| 2 | AGENTS.md | agent 动手前该知道什么 | 仓库根 |
| 3 | 蓝图 | 最终要长成什么样 | `docs/blueprints/` |
| 4 | 当前实现 | 现在实际是什么样 | `docs/architecture/` |
| 5 | 参考 | 某个组件、字段、事件、参数是什么 | `docs/reference/` |
| 6 | 操作 | 一件事怎么做，坏了怎么修 | `docs/guides/` |
| 7 | 决策 | 为什么这么定，否掉了什么 | `docs/decisions/` |
| 8 | 领域知识 | 这个行业的真实规则和术语 | `docs/domain/` |
| 9 | 记录 | 发生过什么 | `docs/records/` |
| 10 | 首页与清单 | hub 怎么走 / 这个目录里有什么 | `docs/README.md` 与各板块 `README.md` |

类型由目录表达，文件名只写主题。不靠 frontmatter 标注类型：GitHub 不显示，多一层标签只多一份要维护的东西。

每类的行数是常见体量，不是判据。判断一段该不该留，用 [`what-good-means.md`](what-good-means.md) 的删句测试。

## 1 README

第一次来的人读完知道：这是什么、跑起来要几条命令、真源在哪、什么情况下别用它。

四十到八十行。安装和运行命令、关键限制、通往 `docs/README.md` 的一条链接。不放架构、不放变更史、不放徽章墙。

## 2 AGENTS.md

agent 动手前的约定：先读什么、真实命令、验证方式、会弄坏东西的操作、禁区。

删到行为不变为止：删掉一行，agent 的行为会不会变？不变就继续删。每条只说工具链推不出来、agent 猜不到的事。

linter 和类型检查已经拦下的规则不抄进来——它们既省不下事，又会在与代码冲突时赢过代码。再补一句冲突裁决（「文档与现有代码冲突时以代码为准，并在回复里指出每一处冲突」）：实测里这一句把跟随代码的比例从 4.2% 提到 91.4%（[arXiv 2610.30571](https://arxiv.org/abs/2610.30571)）。

「超过两百行开始失效」没有出处；原始研究只报了 42% 的文件有上下文膨胀，没给行数阈值。

## 3 蓝图

这个系统最终要长成什么样，为什么是这个形状，怎么算做完。写法见 [`blueprint.md`](blueprint.md)。

六十到一百五十行。每个独立系统一份，放在 `docs/blueprints/`。

## 4 当前实现

现在的模块、数据流、关键路径、真实数值、已知缺口。

几十到一百多行。缺口每条都要能被验证：写「`team/task` 只支持单写者，双开会互相覆盖」，不写「并发处理还不完善」。目标和理想形态属于蓝图，这里只写现在。

## 5 参考

签名、字段、单位、默认值、失败语义、版本。读者带着一个具体符号进来，查完就走。

篇幅由内容决定，可以长。生成的目录类参考（工具目录、配置目录）的长度由生成器决定。

## 6 操作

触发条件、前置、编号步骤、每步的预期结果、失败怎么判断、怎么回滚。

三十到一百二十行。步骤写成能照着做的句子，不写设计理由——理由属于决策。

## 7 决策

背景、选项、选了什么、代价是什么、被否决的方案为什么被否。写完冻结，不随现状更新。

二十到六十行，文件名 `YYYY-MM-DD-主题.md`。要推翻一个决定，写新的一份，不修改旧的。

## 8 领域知识

术语表、业务规则、单位、真实约束、容易混淆的概念。

篇幅不设限，可以分册。写行业里的事实，不写代码结构。做玉雕的写材料与版式，做清算的写科目与对账规则，做实盘的写指标定义。

## 9 记录

日期、输入、结果、结论、教训。只追加，不改写。

单次二十到八十行，按年月分目录。交易复盘、事故记录、里程碑都属于这类。记录里允许长段叙事——它记的是过程，过程本身就是内容。

## 10 首页与清单

两种形态，作用不同，不混在一页。

- **hub**（每个板块的 `README.md`）：3–5 条读者路径，加分组链接，每条一句「什么时候点它」。没有说明的链接等于没有入口。
- **清单**（板块里另建一页）：列全本目录，给已经知道要找什么的人。不做入口。

十到四十行。不引入新事实。骨架见 [`index.template.md`](../templates/index.template.md)。

## 什么内容值得写成文档

判据一句：**这份文档替未来的谁，省掉了什么？** 答不出来就不写；省下的只是一次性的力气，也不写——那种事交给 PR。

更硬的问法：**删掉它之后，未来会不会重新付一次代价？**

值得写：设计取舍（为什么选这条、否掉了哪条）、硬约束（平台、协议、外部系统的限制）、操作（不常用但每次都要正确）、陷阱（会静默出错的地方，最值钱，因为出错时没有报错）、归属（这件事归谁，出问题找谁）。

不值得写：代码结构（读代码更快，而且代码改了文档不会跟着改）、过程（计划、进度、验收清单、审计报告、复盘，完成即废）、重复（同一句话在两处，必有一处会过期）、自我说明（「本文档介绍……」「如有疑问请……」）、口号（严禁、绝对、不得——喊得越响的地方执行得越差）。

## 拿不准的五种情况

**「我怕以后忘了。」** 值得写，但写成决策记录：结论、理由、被否决的方案、什么条件下这个决定会失效，四行足够。

**「这个坑我踩过一次。」** 值得写，写在离代码最近的地方，不是顶层 `docs/`。放在通用文档里，改这段代码的人读不到。

**「网上那篇文章讲得很清楚。」** 不抄，存链接加一句为什么值得看。全文复制会过期，而且没人维护。

**「我研究了很久。」** 过程不值钱，结论值钱。研究过程只在一种情况下留：这个决定以后可能被推翻，而推翻它的人需要知道当时掌握的是哪些证据。

**「这是规矩。」** 先确认这条规矩真的存在。模型经常凭空生成一条「用户要求」，然后它被当成真的传下去。追不到出处的规矩，删掉。

## 抽样自查

随便抽十篇现有文档。超过三篇在记录「某次做了什么」而不是说明「某件事是什么」，这个目录需要清理。
