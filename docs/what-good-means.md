# 什么是好文档

判一份文档改得对不对，看它保留了多少能用的信息，不看它变短了多少。字数、页数、文件数都不是指标。

一句话测试：**删掉这句，读者会失去什么？** 失去事实、条件、步骤、限制、判断依据 → 留着，哪怕很长；只是把同一件事又说了一遍 → 删；读完觉得「说得挺对」但说不出得到了什么 → 删。

这个测试唯一的失败方式是骗自己。

## 系统级九条

单篇写得好只是及格线。一套文档好，是读者带着问题进来，三步之内落到答案，而且答案只有一份。

1. **入口唯一，名字能搜到。** 根 `README.md` → 板块 → 文件，中间最多两次需要猜的分类判断；文件名和标题写成读者会搜的那个词，只记得一个词就能 grep 到。入口按读者第一次进来的顺序排，不按文档类型排。判法见 [`structure.md`](structure.md#读者怎么到)。
2. **板块按读者的问题分，不按代码目录分。** 目录就是问题空间：这是什么、最终要长成什么样、现在是什么样、怎么用、怎么修、为什么这么定、行业里什么是真的、发生过什么。
3. **类型不混。** 蓝图说未来，当前实现说现在，决策说过去，记录只追加。三者挤在一页，就会写出「它不拥有 X、不承担 Y、不是第二个 Z」这种句子——因为作者既要交代目标，又不敢承诺现状。
4. **一个事实一个家。** 其余位置只放链接。
5. **每个板块有 hub，hub 每条带说明。** 3–5 条路径写成读者会问的那句话，加分组链接，一条一句「什么时候点它」。没有说明的链接等于没有入口；列不列全不是判据。
6. **篇幅由主题决定。** 一个文件一个主题，出现第二个主题就拆。目录里多到一眼扫不完时分组。
7. **能回答「我现在该开发什么」。** 读完蓝图加差距表，下一步是具体动作，不是「继续完善」。
8. **齐不齐看清单，不看感觉。** 先列这个仓库必须有的文档清单——来源是代码与包目录、运行态、读者要走的路，不是现有文档——再逐项标「已覆盖 / 半覆盖 / 缺失」。拿现有文档对现有文档，只能验出它自己。
9. **每页从 hub 可达。** 孤儿不只是没人链到的页，也包括从板块 hub 走不到的页：读者导航不到，改动也没人看得见。新增一页就在同一次改动里挂到 hub；挂不上就补层或者删掉。

## 否定不能当定义

最典型的坏文档：半句定义，然后用一串"不"把它围起来。真实现场，一段四句里三句半在说它不是什么（SiNS `docs/sins/external-projects.md` 改前）：

> 它不把外部项目的全部实现引入 SiNS，也不替代本地架构和源码的 authority。
> 本页只索引，不复制第二份实现合同。
> 下表中的"采用"包含 IDEA，不表示安装了对应第三方软件。
> 集成研究案例，非已采用声明。

四句里能执行的只有一条：表中的"采用"包含 IDEA。其余三句在挡一个作者想象出来的误读者。读者读完仍然不知道这页记什么、什么时候该来看它。

共同结构是**半句是什么 + 两三句不是什么**，命中的词是「不替代」「不代表」「不构成」「不引入」「非…声明」「本页只…」。

### 判据

删掉这个否定，读者会不会**做错事**——不是会不会误读。误读是作者想象出来的，做错事是真的。

- 有人会开错开关、写错数据、跳过必要步骤 → 保留，但写成具体动作：「`uncertain` 不能转换成 `pass`」。
- 只是"可能有人误会" → 删。

### 三种改法

| 原句 | 改法 | 改后 |
|---|---|---|
| 它不替代本地架构和源码的 authority | 写归属 | 架构与源码的 authority 在 `architecture/` 和源码本身 |
| 本页只索引，不复制第二份实现合同 | 删 | 上一句已经在说入口关系，到此为止 |
| Commander 不是独立调度主体 | 正确定义 | Commander 是 Main 的一个分工角色：借 Agent Team board 组织任务 |
| 不拥有 durable truth | 点名持有者 | durable truth 由各 owner 持有 |
| 集成研究案例，非已采用声明 | 说得更准 | 研究候选，尚未采用 |

顺序：能给出定义就给定义；定义已经在上一句，就把边界改成归属；两样都不需要，删。

一个自然段最多一个否定，并且指向一个具体动作。超过一个，说明这段在用排除法代替定义。

定义要说它**是**什么，精确到读者能拿这一定义判断一个新例子算不算。亚里士多德《论题篇》第六卷第六节把「用否定来划分」列为定义错误：线不能定义成「无宽度的长度」。Strunk 第三条：说它是什么，不说它不是什么。

## 五种没有信息的句子

| 长这样 | 为什么会出现 | 换成 |
|---|---|---|
| 实际情况可能不同，请结合具体情况判断 | 不想负责 | Windows 上这条命令需要管理员权限 |
| A 和 B 各有优劣，应综合考虑 | 没做决定 | A 冷启动快 3 秒，B 才支持断点续传；这里要断点续传，选 B |
| 系统追求稳定，这体现了对可靠性的重视 | 把一个事实说了两遍 | 失败后保留任务 ID，重试不重复下单 |
| 本仓库致力于打造专业、规范的工程体系 | 声音大，信息零 | 每个仓库只有一个 owner；跨仓库依赖写在拥有它的那个仓库里 |
| 后续还需要注意许多潜在问题 | AI 的收尾习惯 | 写出已知的失败条件；不知道就整句删掉 |

## 审查挑真问题

审查的价值在区分「会改变结论的问题」与「理论上可能的问题」。没有依据的挑刺、为了完整而罗列边缘风险、把个人风格差异判成缺陷，都在增加读者的成本，而不是提高质量。

指出问题的同时要说清它为什么成立、影响多大、最有价值的修正方向。审查不是增加约束和流程的理由。

文档没有问题时明确说通过。为了证明审查有价值而制造发现，比漏掉一个真问题更坏。

## 什么不是废话

三类内容看着像废话，删了会出事：

| 类型 | 例子 | 为什么留 |
|---|---|---|
| 记录与证据 | 交易复盘的时间线、审计的逐条发现 | 长度由事实量决定。日期、原话、测量值、失败痕迹，代码和提交历史重建不出来 |
| 硬约束与禁止句 | 某个开关关闭后权限仍然生效；某种状态下列为 `NO_TRADE` | 这个"不"本身就是安全事实，删掉会让人做错事 |
| 未确认的事 | 还没做过真实验收、这条路径未在 Windows 上验证 | 写清边界才叫说完了；不写等于假装已经完成 |

把这些压掉，数字确实会更好看的，文档也确实没用了。所以整理时的判据是逐句问「这句有没有信息」，不是把某一类词的出现次数压到零。

## AI 留下的痕迹

**给下一个模型的指令。**「后续助手不可自行修改」「请谨慎处理此段」。文档写给读的人，不是给执行者下命令。这类句子会被下一个 agent 当成规则继承，一代代传下去。

**审稿记录。**「本条从旧版合并」「此处推断尚需核实」「为避免误解特此保留」。编辑过程不属于文档内容。

**自我表扬和免责。**「本方案科学、严谨、可扩展」「它不改变权限，也不建立第二数据库」。删掉之后如果什么都不剩，说明本来就没有内容。

**为了显得周到而多加的对称小节。** 每个文件都要有「背景」「目标」「范围」「风险」，其中一半是空的。「由此引出」「这样一来」「值得注意的是」这类垫话同样属于此列。

更隐蔽的一类：**元叙述**。文档在讲自己——「本页不复制 X，以 Y 为准」「本文档只记录当前状态」。读者要的是状态本身，不是你对状态的声明。

## 判句不装成检查器

文档质量靠读，不靠数。字数上限、强制换行、禁用词表、每节必须存在——这些能算出数字，算不出读者得到什么。字数上限让文字变短，短不等于有信息；禁用词表把一次判断换成一张要持续维护的例外清单。

现成的失败案例。SiNS 曾用 `verify-doc-budgets` 给常在文档设字数天花板：`architecture.md` 在标准里写着 1,800 词目标，清单里允许 2,400 词，文件当时 1,313 词。门禁一直通过，因为它量的是清单里的数，不是标准里的目标。同一个系统还有 100 词的包 README Summary 上限和禁止硬换行的检查。三个都在 2026-10-29 删除，判断交回给读的人；理由记在 SiNS `.agents/notes/implemented/process/2026-07-04-doc-tiers.md` 的替代方案一节。

分工因此固定：产品仓库用机器检查它能真正判定的东西——编译、类型、链接、安装产物、行为回归；怎么写留在这里。这个仓库不分发检查器，也不接受把上面的判据编译成脚本再放回产品仓库。

## 精简不是摘要

把三行的路径信息压成一行，不叫优化。

原句：DESKTOP 与 LAPTOP 两台机器的工作树都在某个路径；某个脚本负责 Git 同步，Motherland 记录拓扑，CBM 负责实时代码图。被压成「使用脚本同步代码」之后，两台机器、路径、责任边界全没了。

改对的方式是删掉重复的解释，不是删掉事实。

## AGENTS.md 最容易写坏

先说结论：这类文件整体上不提高任务成功率，反而让推理成本涨两成以上；指令本身被遵守得很好，「仓库概览」这类内容实测无用，真正有用的是这个仓库的非标准做法（[arXiv 2602.11988](https://arxiv.org/abs/2602.11988)，SWE-bench 任务与含开发者手写上下文文件的仓库两套设置，跨多个模型与 agent 成立）。所以下面六种毛病不是文风问题，是收益问题。

对 100 个开源仓库、207 个实例的统计给出六种典型毛病（[Configuration Smells in AGENTS.md Files](https://arxiv.org/abs/2606.15828)，SCAM 2026）：

| 毛病 | 占比 | 表现 |
|---|---|---|
| Lint 泄漏 | 62% | 把 linter、formatter、类型检查已经拦下的规则又抄一遍 |
| 上下文膨胀 | 42% | 长到 agent 记不住；删到行为不变为止 |
| 技能泄漏 | 35% | 把该按需加载的技能内容整段贴进常驻文件，每轮都付这份上下文 |

摘要还点了第四种「互相冲突」，并说明这三种常与它结伴出现。它的具体占比我没在原文核到，不写数字。冲突贵的地方不是读者看不懂，而是他得靠加更多解释来打补丁。

另外两类我常看到、但拿不出可靠比例的毛病：一列反引号路径，每个后面没有一句说明（读到的人不知道该点哪个，也不知道哪几个现在还有用）；只是 `/init` 生成过一次、从没再改的化石文件。这两条判起来不需要数字——看一眼就知道。

## 具体到文件

| 文件 | 删了会出事的内容 |
|---|---|
| 根 `README.md` | 安装和运行命令、关键限制、通往 `docs/` 的链接 |
| `AGENTS.md` | 真实命令、验证方式、会弄坏东西的操作 |
| `docs/README.md` | 板块划分和每篇的一句话定位 |
| `CODEMAP.md` | 那几跳以及它们为什么是起读点 |
| 蓝图 | 目标形态、验收判据、差距表 |
| 决策记录 | 被否决的方案和否决理由 |
| 参考文档 | 数据结构、字段语义、失败表现 |
| 操作文档 | 前置条件、每一步的预期结果、出错怎么判断 |

## 改完检查三样

1. **命令还能不能跑。** 改过路径和参数就实际跑一次。
2. **链接还通不通。** 移动过文件就重扫全仓库的 markdown 链接。
3. **删掉的东西里有没有只此一份的事实。** 删之前没确认，删之后只能翻 git 历史。

不需要额外备份（git 历史就是备份），不需要更正说明，不需要在 changelog 里补一笔。

这三样是检查，不是通过的判据。文档算不算干净只看它自己：每句有没有信息、有没有在讲它自己、有没有交代到别人能照着做。链接全通、引用全在，也可能整页是废话；反过来，一篇没人引用的重要文档照样算数。

这不排斥机械检查，只要它比的是值而不是意义：脚本能可靠地回答「文档里那个端口和配置文件里的不一样了」，那是比对；「这段文档还有没有用」仍然要人或者 agent 判断。把前者做成门禁是对的，把后者做成门禁就是拿分数替换判断。

## 怎么找出最差的页

按这三个信号排序，读完前五页就够：

1. **防误读否定密度。** 搜「不替代|不取代|不复制|不引入|不代表|不构成|非…声明|本页只」，再加上推理类的「不能据此|不足以证明|不能证明|只能说明|不等于」，一行命中两次以上、一页命中五次以上，基本是重灾区。整页词表长什么样、怎么改，见 [`examples.md`](examples.md#否定词云)。
2. **公理复述。** 拿一个核心概念去搜，出现在五个以上文件，说明同一套原则被几页各自重讲。单个事实进到第二个文件就该合并，这条查的是更宽的原则级重复。
3. **空清单。** 表格里有整列是破折号或"待核"，说明这批条目还没被判断过。

第 1 类改句子，第 2 类合并到一个家，第 3 类删或补判断。三类都不影响结构和链接，所以可以一次性改完，不必边改边重读。
