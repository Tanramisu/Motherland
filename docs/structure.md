# 目录结构

## 读者怎么到

目录结构回答「写的时候放哪」，不回答「找的时候从哪进」。三百个文件全在索引里，读者照样可能连着点错三次。Google 内部 wiki 就是这样：命名空间平铺、文档都在，同一个主题却有 7 到 10 份互相竞争的说法，废弃时九成文档几个月没人看过；Auth0 重整前一千多页文档里 75% 有导航错误、54% 根本不在导航里（[SWE at Google 第 10 章](https://abseil.io/resources/swe-book/html/ch10.html)、[Auth0 案例](https://madebymax.dev/design/docs-ia/)）。**索引证明文档存在，hub 证明读者找得到。**

| 层 | 放什么 | 读者 | 要求 |
|---|---|---|---|
| 定向 | 这是什么、为什么是这个形状、怎么跑、哪些边界不能碰 | 没有具体问题的人，第一次来或半年后回来 | 从根 `README.md` 一跳可达 |
| 板块首页（hub） | 一组相关材料的入口 | 知道大致方向、不知道该点哪一个 | 每个板块一个，3–5 条路径加分组链接 |
| 细节 | 参考、决策、记录、某次复盘 | 带着具体问题来 | 只能由 hub 或上一层进入，越深越具体 |

### 读者是 agent 时，这条线更硬

agent 不沿目录树走，它拿文件名和关键词去 grep；它也不读导览——「仓库概览」这类内容实测无用，数据和机制见 [`what-good-means.md`](what-good-means.md#agentsmd-最容易写坏)。

所以：一页只解决一个问题，页名就是检索词；命令写在能被直接复制的块里；不建面向 agent 的目录站或 `llms.txt`——137,210 个域名里 28% 发布了 `llms.txt`，其中 97% 在 2026 年 5 月零请求（[Ahrefs 日志研究](https://ahrefs.com/blog/llmstxt-study/)，站点级观测，非对照实验）。

### 先说名字，再说层级

**链接标签的质量是决定因素，不是层级。** 模拟加实测的同一份研究（Miller & Remington，*Human-Computer Interaction* 19(3), 2004）里，标签质量单独解释导航时间方差的 58.2%，作者的原话是它比结构更重要；而且**标签清晰时三层比两层快**，标签含混时两层才更快（[PDF](http://facweb.cs.depaul.edu/cmiller/hci2004.pdf)）。层级是标签的结果，不是前提。

落到仓库上，文件名和标题就是标签。`restart-and-resume.md` 优于 `ops.md`，`current-design.md` 优于 `overview.md`。判断法：只记得一个词，`grep -r` 能不能命中；命中的那几页，标题能不能一眼分出要找的那份。

### 三条能当场判的线

1. **一条路径上最多两次「猜」。** 猜指读者得凭猜测决定点哪个。第三次开始要回头重走，这正是标签含混时三层变慢的机制。
2. **顶层五到十个链接。** 菜单实验里每页约八个选择最优，超过八个变慢，除非选项本身已按字母或明显类别排好；常被引用的「三次点击」没有数据支持（[NN/G](https://www.nngroup.com/articles/3-click-rule/)），点击次数不预测成功。
3. **每一层比上一层更具体。** 「文档 → 架构 → 丘脑」是往下走；「文档 → 其他 → 杂项」是往回走。

深度本身不是判据：标签清晰时多一层几乎不收费。硬写「不超过三跳」，逼出来的是把不相关的东西塞进同一页，标签反而更含混。要压就压含混的那一层。

### 什么进定向层

判据一句话：**一个还没有具体问题的人，第一次进来会不会需要读它？**

会，就是定向层：这个系统是什么、为什么这样、怎么跑起来、哪些边界不能碰、下一份该读什么。不会，往下放。

设计原则、目标形态、硬约束属于定向层。它们决定读者后面怎么理解一切；埋在三级目录的第三个文件里、要先猜该点哪个板块才到得了，等于没写。

### hub 的价值全在说明

hub（每个板块的 `README.md`）本身不解决到达问题：证据里它的解释力最低，起作用的是每一条链接后面那句话。一条路径写成读者会问的那句话，加一句「什么时候点它」，骨架见 [`index.template.md`](../templates/index.template.md)。

列不列全不是判据。列全但每条没有说明，读者照样一个个点进去；只列一半但每条说清了，反而更好。要全量清单时另建一页，那页给人查，不当入口。

新增一页只需动两处：新建文件，加 hub 里那一行。要动第三处，说明这页挂错了板块。

从任何 hub 都走不到的页是孤儿。Sphinx 对没进目录的页直接报警，Markdown 仓库要自己查。

agent 不按 hub 走，它按文件名和命令干活。所以 `AGENTS.md` 里写「仓库概览」这类导览没有用处：实测既不提高成功率，成本还涨两成（[arXiv 2602.11988](https://arxiv.org/abs/2602.11988)）。

### 怎么验

不数链接，做一次 wayfinding：拿三个真实问题（改这个行为要动哪几处、这个开关关掉会怎样、上次怎么坏的），让别人只靠文档找，记下第一跳点了哪、错在哪。三个问题都在两次之内落到答案，结构就够用；点错两次以上，是板块命名或分层的问题，不是索引的问题。Auth0 用的就是这个办法，加卡片分类定分组。

## 默认骨架

按需裁剪。不需要的板块整个删掉，不留空目录、不写「本板块暂未启用」。

```
repo/
├── README.md
├── AGENTS.md
└── docs/
    ├── README.md          这一层的索引：每个板块给谁看
    ├── blueprints/        最终要长成什么样
    ├── architecture/      现在是什么样
    ├── reference/         组件、字段、事件、配置、参数
    ├── guides/            操作与排障
    ├── decisions/         决策记录
    ├── domain/            行业规则与术语
    └── records/           复盘、事故、里程碑
```

目录名全仓统一用这七个英文词。文件名用该仓库的主语言，不混用、不用拼音。SiNS 这类英文仓库用 kebab-case；中文仓库用中文主题名（`丘脑.md`、`清算美术史.md`）。

日期前缀只出现在 `decisions/` 和 `records/`。其它文件名不写日期、不写版本号——`-v2`、`-new`、`-final`、`-旧` 一律不允许。

## 三个位置，三种触发条件

| 位置 | 谁在什么时候打开它 | 放什么 |
|---|---|---|
| `README.md` | 第一次到这个仓库的人或 agent，还不知道它是什么 | 这是什么、怎么跑、从哪读起 |
| `AGENTS.md` | agent 动手之前，每一轮都读 | 命令、约定、禁区、改完怎么验 |
| `docs/` | 带着一个具体问题来的人和 agent | 蓝图、现状、参考、操作、决策、领域、记录 |

三个位置都能被 agent 读到，区别在它什么时候读、拿它做什么：README 回答「要不要用这个东西、从哪开始」，是判断入口；AGENTS 回答「这次动手必须遵守什么」，每轮进上下文，所以要短；`docs/` 回答「这一件事的细节」，按关键词取一页就走。

正因为它每轮都进上下文，AGENTS 里只留猜不到的约束：真实命令、会弄坏东西的操作、和别处不一样的做法。仓库地形——目录清单、包列表、模块名册——不写进去，`ls` 比它更快，而且文件挪了它不会跟着改。

## 一个事实只有一个家

同一段规则同时写在 `README.md` 和 `AGENTS.md` 里，两处措辞不同，读者不知道以哪个为准。写之前先搜一遍：已经有了就改那处，不新建第二处。

同一条公理被几页各讲一遍，比同一段规则写两遍更坏：每份都不全，读者要自己拼，改一处就漂一处。实测 Liquidation 的 `docs/清算美术设计/`，同一个「操作者坐在多屏工作位、只看到机构的一个切面」——「切面」出现在 9 个文件，「多屏」6 个，「总操作席」5 个，「冰山」3 个，四层各有自己的一版说法。

做法：第一次写它的文件是家，其余位置用一句「见 X」，或者干脆不再提。判断方法：同一个事实出现在第二个文件里，就该合并，其余位置只留链接。同一套原则被几页各自重讲，用 [`what-good-means.md`](what-good-means.md) 的「怎么找出最差的页」处理。

## 什么时候不按这七个目录分

三种情况保持原样，把理由写进该仓 `docs/README.md`，然后不再动它：

- **外部工具按字面路径读。** 生成器、打包器、上游项目会在代码里写死 `docs/persistence-changes/`、`docs/cordis-api/` 这类路径，物理改名等于让六个脚本一起坏。这时 `docs/README.md` 用一张「类型 → 路径」对照表，把类型语义补回来。
- **同一个事实被几套系统共读。** 硬件仓按 `hardware/`、`firmware/` 组织，是因为引脚表同时被固件、接线图和采购单读；拆成七个类型目录反而要把一个部件的三份事实分散到三处。
- **上游归档。** fork 或第三方镜像的内容原样保存，改一个目录名，下次同步就是全仓冲突。

判断口径：能改就改成七型；改的代价来自外部约束而不是写作习惯时，保留结构、补一张类型对照表。

## 层数越少越好

反例：`docs/业务研究/钻石行业/产业与启动/原始报告/`，四层。找一份文件要点四次，而中间每层实际只有一个分支。

判断方法：**某一层只有一个子目录，它就不该存在。**

路径深度上限三层：`docs/<板块>/<子板块>/<文件>`。需要第四层时，说明板块划分错了，回头合并。

## 什么时候拆

单文件一个主题。长不是问题：`docs/persistence-catalog.md` 九千五百多行，因为它只有一件事。一页里出现第二个主题，才是该拆的信号。

该拆的信号：出现第二个主题、出现第二个读者群。

不该拆的理由：纯表格或目录式参考（工具目录、配置项清单、事件表）。生成类参考的长度由生成器决定。

## 目录里放多少个文件

按主题分，不按数量分。索引在一屏里扫得完、每个文件名都能看出是干什么的，就还可以不分；翻两屏还找不到目标，说明这里混了两个主题，该分。

三个文件分进三个子目录是错的：找的时候要开三次。

## 入口是文档

`docs/` 有内容却没有 hub，等于没有文档。根 `README.md` 至少有一条能点开 `docs/README.md` 的链接；`docs/README.md` 与每个板块的 `README.md` 都是 hub，写法见上面「hub 的价值全在说明」。

入口按读者第一次进来的顺序排（这是什么、怎么跑、下一步读哪），不按文档类型或目录骨架排。分类决定写的时候放哪，不决定找的时候从哪进。

索引不引入新事实，只做导航（类型 10，见 [`doc-types.md`](doc-types.md)）。

## 什么时候需要 CODEMAP

不是每个仓库都要。README 的「从哪读起」够用，就不需要 CODEMAP：十个以内的模块、一两层目录，熟悉的人扫一眼就知道开哪个文件。

需要它的情况：问题「改这个行为要动哪几处」的答案跨越十几个目录，而且每次都要重新拼一遍。这时缺的不是搜索能力，是第一跳该落在哪。

| | 回答什么 | 谁维护 |
|---|---|---|
| CODEMAP | 从哪开始读，读完转到哪 | 手写，随结构缓慢更新 |
| 代码图 | 这个符号被谁调用、影响哪些文件 | `codebase-memory-mcp`，实时 |

把代码图抄进 CODEMAP，第二天就过期。[C4 模型](https://c4model.com/diagrams/faq)的作者对代码级图的结论是「不画，或者用工具按需生成」，理由是它的变化速度超过任何人的维护速度；他给的一般判据是**每一层的有效寿命由它的变化速度决定**，所以文档里只放变得慢的东西——目录、职责、主干流程，不是文件名和符号。

过期的图比没有图更糟：读者照着它找错地方，而且不再怀疑。一项对三千多个 GitHub 仓库的检测（[Detecting outdated code element references](https://doi.org/10.1007/s10664-023-10397-6)，EMSE 2023）发现，失效引用最后有 13.3% 是靠直接删掉那段文档收场的。

## 一份 CODEMAP 里该有什么

一项对十二场真实 onboarding 的观察研究（[Characterizing the transfer of program comprehension in onboarding](https://link.springer.com/article/10.1007/s10664-019-09741-6)，EMSE 2019，八家公司）归纳出专家向新人传递理解的四项视图：

- 结构：代码里有什么，怎么分块，哪块是主体，哪块是外围。
- 流程：一个功能实际怎么跑起来，拆成几步。
- 理由：功能需求和非功能需求，以及它们如何决定了现在的设计。新人评价这一项价值最高。
- 时间：在改什么、改过什么、接下来要改什么。

结构和流程由 CODEMAP 承担；理由交给决策记录，时间交给提交历史。把后两项写进 CODEMAP，它第二天就假了。

[arc42](https://docs.arc42.org/section-5/) 对结构视图的要求是「宁可相关，不要完整」：只写重要的、意外的、有风险的、复杂的、易变的部分，省掉普通和标准的部分。

判断一条该不该进 CODEMAP：删掉它，下次找同一个地方会不会变慢。不会，就删掉。

## 跨仓库的事写在哪

写在拥有这件事的仓库里，不写在 Motherland。

Motherland 只记三样：仓库在哪、文档该怎么写、模板长什么样。
