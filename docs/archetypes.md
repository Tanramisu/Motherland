# 项目原型

不是每个仓库都要十个板块。先判定它属于哪种形状，再决定建哪些目录。判错的代价是长期维护一堆用不上的东西。

## 怎么判定

问三个问题，答案决定原型：

1. **它产出的是运行的软件，还是决定、记录与内容？** 前者要 `architecture/`，后者要 `domain/` 与 `records/`。
2. **谁读它：使用者、维护者、还是只有你自己？** 只有你自己读的仓库（业务台账、创作、实盘）砍掉对外板块。
3. **它有没有被别人依赖的运行产物？** 有部署、有定时任务、有对外接口，才需要 `guides/` 里的排障与恢复。

判定结果写进该仓库的 `docs/README.md` 第一段，后来的人不用重新猜。

## 八种原型

| 原型 | 典型仓库 | 必需板块 | 明确不要 |
|---|---|---|---|
| A 平台 / harness | agent 平台仓库 | README、AGENTS、blueprints、architecture、reference（按子系统分）、guides（cookbook）、decisions、records | 用户教程、营销文案、教程式入门 |
| B 部署与运维 | 双机运维、设备部署仓库 | README、AGENTS、blueprints、architecture、guides（runbook 与排障）、reference（任务、配置、端口）、records（事故） | domain、产品蓝图 |
| C 产品 / SaaS | SaaS 与内容产品仓库 | README、blueprints（产品目标）、architecture、reference（接口、配置）、guides（上手、发布）、decisions、records | 大段内部调研 |
| D 业务台账 | 业务台账仓库 | README、AGENTS、domain（业务规则、科目、术语）、guides（日常记账、对账）、reference（表单、字段）、records（月度台账）、decisions | 代码架构（没有代码就整块删） |
| E 研究 / 实盘 | 研究与实盘仓库 | README、AGENTS、blueprints（策略目标与验收）、domain（指标定义、规则）、reference（参数）、records（研究结论与复盘） | 空泛方法论 |
| F 设计 / 创作 | 设计与创作仓库 | README、blueprints（风格目标）、domain（设计语言、材料、版式、语法）、guides（生产流程）、reference（尺寸、参数、工具）、records（方案与反馈） | 工程架构 |
| G 治理基准 | 本仓库 | README、AGENTS、REPOS、`docs/`（规范本身）、`templates/` | 任何具体项目的文档 |
| H 上游镜像 / fork | 上游镜像、游戏 mod fork | 纯镜像：README（来源、版本、许可、本仓改了什么）、ATTRIBUTION；fork：另建 `docs/` 装自有部分 | 纯镜像不建 `docs/`；上游正文一字不改；上游文件不重写、不译 |

## A 平台 / harness

板块按子系统分，不按代码目录分。`reference/` 下最常见的是"一个子系统一份"，读者带着符号名或事件名进来，落到那一页。

`guides/` 放"加一个新工具""加一个新适配器"这类操作，一个动作一篇。

不需要入门教程：平台的使用者是维护它的人，教程留给有真实外部用户的项目。

## B 部署与运维

`guides/` 是这类仓库的主体：每个定时任务、每条恢复路径各一篇 runbook，写触发条件、前置、步骤、验证、回滚。

`records/` 记事故：时间、现象、真实原因、修复、防复发。事故记录允许长——过程本身就是内容。

`architecture/` 只写拓扑、端口、路径、账号归属、依赖关系这些变得慢的东西。

## C 产品 / SaaS

`blueprints/` 写产品目标：谁在用、解决什么、什么算成功。`reference/` 写接口和配置项。`guides/` 分"新用户怎么上手"和"怎么发布一版"。

面向客户的正式文档不在这里：它有自己的站点和位置，仓库里只留一句指路。

## D 业务台账

没有代码，就没有 `architecture/`。主体是 `domain/`（业务怎么运转、科目怎么定义、对账规则）和 `records/`（每月实际发生了什么）。

`guides/` 写日常操作：怎么录一笔、怎么对账、怎么发现差额。

这类仓库最容易被塞进"方法论"文章。判据是：删掉它，下次做同一件事会不会做错。不会，就删。

## E 研究 / 实盘

`blueprints/` 写策略要达到什么、怎么算有效（可测的判据，例如回撤上限、样本量、胜率区间）。

`domain/` 写指标定义与规则：某个指标怎么算、什么信号视为无效、仓位与止损的硬约束。

`records/` 是主体：每个决策当时的输入、结果、复盘。复盘允许长段叙事，但要写清"当时掌握的证据"和"事后看哪一步错了"。

## F 设计 / 创作

`domain/` 是核心：设计语言、材料事实、版式规则、语法。这类知识代码里没有，别人也不会替写。

`blueprints/` 写风格目标与验收：什么样的成片算合格，用什么判据判断（比例、材质、色域、结构）。

`records/` 存方案与反馈：输入、三个候选、你的选择、意见、下一轮改了什么。

## G 治理基准

这类仓库的产物是「别的仓库怎么写文档」这条规则本身，所以七个板块一个都不建：没有蓝图、没有架构、没有参考、没有记录。

- `README.md` 写判据：什么算好、模板在哪、什么不归这里管。
- `AGENTS.md` 写动手顺序和硬规则，判据不在两处各写一遍。
- `REPOS.md` 记仓库在哪：本地路径、有没有 checkout、出问题找谁。公开仓库里只放示例表，真实清单本地维护。
- `docs/` 放规范本身，一页回答一个判据问题：类型、结构、落笔、生死、齐不齐。
- `templates/` 放能直接抄的骨架，每份开头的注释写清读者是谁、抄的时候删什么。

规范之间互相链接，不互相复述：同一条判据写在两处，改一处另一处就假了。

## H 上游镜像 / fork

只写本仓库自有部分：来源仓库与版本、许可、本仓改了什么、怎么同步上游。

上游正文一字不改——改了就无法再同步。

纯镜像放 `README.md` 与 `ATTRIBUTION.md`，不建 `docs/`。

fork 出了自己代码的建 `docs/`，但只装自有部分：自有工具与接口参考、自有发布流程。上游文件留在原路径，不为它们写中文说明，也不重写进自己的页。

## 常见判错

- **给业务仓库建 `architecture/`**：没有代码，写出来的是想象中的架构。
- **给平台建 `domain/`**：领域知识在它服务的业务方那里，抄进来就过期。
- **所有仓库都建满十个目录**：空目录比没有目录更糟，它教后来的人"这里应该有点东西"。
- **把镜像仓库当成自己的项目**：给它补文档，等于给上游写第二份会漂移的说明书。
